# پرسش و پاسخ جلسهٔ دفاع

### این پروژه چه می‌کند؟
یک MCP Gateway مینیمال: کاربر login می‌کند، از کاتالوگ tool انتخاب می‌کند، platform token می‌گیرد، و کلاینت فقط همان toolها را می‌بیند.

### ادمین و کاربر چه فرقی دارند؟
ادمین کاتالوگ MCP (افزودن چند سرور، Sync، حذف) و کاربران را مدیریت می‌کند. کاربر Gateway خودش را از لیست می‌سازد و بعداً toolهایش را ویرایش می‌کند.

### چرا دو نوع token دارید؟
Session برای داشبورد وب است. Platform token برای کلاینت AI و endpoint مربوط به `/mcp` است.

### آیا می‌شود toolهای یک Gateway را بعداً عوض کرد؟
بله. در «Gateway من» روی «ویرایش toolها» بزنید؛ allowlist همان token عوض می‌شود و خود token ثابت می‌ماند.

### اگر کسی نام tool را بداند ولی grant نداشته باشد؟
`tools/call` رد می‌شود.

### توکن خام کجا ذخیره می‌شود؟
هیچ‌جا در database؛ فقط hash. خام یک‌بار در UI نشان داده می‌شود.

### چرا SQLite؟
برای دمو و دفاع سبک و کافی است.

### ارزیابی‌تان چیست؟
کاربر Gateway با فقط `notes_list` می‌سازد؛ list فیلتر می‌شود؛ call غیرمجاز رد و call مجاز موفق است. این سه رفتار با `./scripts/eval_scenarios.sh` خودکارند. ویرایش بعدی grant (افزایش/کاهش) سناریوی دستی/دمو است، نه بخش اسکریپت خودکار.

### برای شرکت واقعی کافی است؟
به‌عنوان هسته مفهومی بله؛ برای production نیاز به OAuth/audit/مقیاس بیشتر دارد.

### چرا چند پروتکل (stdio / SSEهای مختلف) را پشتیبانی نکردید؟
عمدی است. هستهٔ کار allowlist و platform token است. یک مسیر remote HTTP برای کلاینت کافی و قابل دفاع است؛ multi-transport پیچیدگی اضافه برای پایان‌نامه می‌آورد.

### پس MCPهای عمومی که هدر/API key می‌خواهند چطور؟
آن نیاز سمت **upstream** است، نه کلاینت. هنگام ثبت سرور، `auth_header` اختیاری به‌عنوان مقدار هدر `Authorization` ذخیره می‌شود و Gateway همان را هنگام Sync/پروکسی می‌فرستد. کلاینت AI همچنان فقط `Authorization: Bearer mcpgw_...` می‌گذارد و هدر upstream را نمی‌بیند.
