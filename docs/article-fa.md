# طراحی و پیاده‌سازی MCP Gateway مینیمال برای تجمیع MCP serverها و access control در سطح tool

**مقالهٔ کامل پایان‌نامه کارشناسی**  
**سامانهٔ پیاده‌سازی‌شده:** `mcp-gateway`

---

## چکیده

با گسترش AI agentهای ابزارمحور، اتصال مدل به toolهای خارجی به نیازی اساسی تبدیل شده است. پروتکل Model Context Protocol (MCP) کشف و فراخوانی toolها را استاندارد می‌کند؛ اما در عمل مدیریت چند MCP server معمولاً پراکنده است و access control در سطح tool ضعیف است. این پژوهش کاربردی یک MCP Gateway مینیمال طراحی و پیاده‌سازی می‌کند که در آن ادمین کاتالوگ MCP را مدیریت می‌کند، کاربر با username/password وارد می‌شود، از لیست tool انتخاب می‌کند، platform token می‌گیرد، و ترافیک `tools/list` و `tools/call` طبق allowlist فیلتر می‌شود. سامانه شامل Backend، UI فارسی/RTL، demo MCP کاربردی (notes/tasks)، و سناریوهای ارزیابی است. نتیجه نشان می‌دهد با معماری ساده می‌توان فلو کاربرمحور و دو رفتار کلیدی دسترسی را تکرارپذیر نشان داد: فقط toolهای مجاز دیده شوند و call غیرمجاز رد شود.

**کلیدواژه‌ها:** MCP, MCP Gateway, access control, platform token, AI agent, tool proxy

---

## ۱. مقدمه

### ۱.۱ زمینهٔ موضوع

مدل‌های زبانی بزرگ اگر فقط متن تولید کنند، در بسیاری از سناریوهای واقعی ناتمام می‌مانند. وقتی مدل بتواند tool call انجام دهد—مثلاً محاسبه، بازیابی اطلاعات، یا اجرای یک عمل مشخص—ارزش کاربردی آن بیشتر می‌شود. برای منظم‌کردن این ارتباط، پروتکل‌هایی شکل گرفته‌اند که AI client را به tool server وصل می‌کنند. MCP در همین فضا، توصیف tool، کشف فهرست toolها و اجرای آن‌ها را استاندارد می‌کند.

### ۱.۲ اهمیت موضوع

اهمیت کار از سه جهت است:

1. **عملی:** تیم‌های کوچک و محیط‌های آموزشی به یک نقطهٔ اتصال واحد نیاز دارند.  
2. **امنیتی:** نمایش همهٔ ابزارها به همهٔ کاربران سطح حمله را بالا می‌برد.  
3. **آموزشی:** برای دفاع کارشناسی، سامانه‌ای لازم است که هم قابل توضیح باشد و هم در چند دقیقه قابل نمایش.

### ۱.۳ بیان مسئله

در اتصال مستقیم کلاینت به چند سرور MCP، این مشکلات تکرار می‌شود:

1. پیکربندی چندتکه و تکراری در هر کلاینت  
2. نبود لایهٔ متمرکز برای محدود کردن ابزارها  
3. دشواری اشتراک امن دسترسی بدون فاش کردن جزئیات upstream  
4. فاصله بین ایدهٔ نظری کنترل دسترسی و یک اپلیکیشن کوچک واقعاً قابل استفاده  

مسئلهٔ این پژوهش چنین است: طراحی و ساخت لایه‌ای مینیمال که چند MCP server را تجمیع کند، هویت اتصال را با platform token مدیریت کند، و دسترسی را در سطح tool اعمال کند.

### ۱.۴ سؤال‌های پژوهش

1. چگونه می‌توان چند سرور MCP را پشت یک endpoint واحد قرار داد؟  
2. چگونه می‌توان با platform token، زیرمجموعهٔ مجاز ابزار را برای هر اتصال تعیین کرد؟  
3. آیا می‌توان با یک پیاده‌سازی مینیمال، دو رفتار حیاتی دسترسی (فیلتر list و رد call غیرمجاز) را اثبات کرد؟  

### ۱.۵ اهداف

**هدف اصلی:** طراحی و پیاده‌سازی MCP Gateway مینیمال با قابلیت تجمیع و کنترل دسترسی سطح ابزار.

**اهداف فرعی:**

- جداسازی مسیر مدیریت از مسیر اجرای ابزار  
- ارائهٔ رابط کاربری ساده برای دمو  
- فراهم کردن demo MCP برای ارزیابی مستقل از دامنهٔ پیچیده  
- مستندسازی کامل برای دفاع  

### ۱.۶ فرضیه‌های کاری

- اگر سیاست allowlist در gateway اعمال شود، کلاینت حتی از وجود ابزار غیرمجاز در list مطلع نمی‌شود.  
- اگر فقط نام ابزار دانسته شود ولی grant نباشد، call باید شکست بخورد.  
- مینیمال بودن معماری مانع تحقق این دو رفتار نیست.

### ۱.۷ محدوده و موارد خارج از محدوده

**داخل محدوده:** login کاربر با username/password، نقش ادمین/کاربر، ثبت remote MCP server، هدر احراز upstream اختیاری (`auth_header`) برای MCPهای عمومی/hosted که API key می‌خواهند، sync ابزار، صفحهٔ Gateway من برای انتخاب tool، صدور platform token، پروکسی `tools/list` و `tools/call` روی یک مسیر HTTP استاندارد، UI فارسی/RTL، دمو، ارزیابی دسترسی.

**خارج از محدوده:** پشتیبانی هم‌زمان چند transport کلاینت (مثل stdio و چند گونه SSE)، OAuth سازمانی کامل برای کلاینت، خوشه‌بندی و مقیاس ابری، میزبانی فرایندهای محلی پیچیده داخل Gateway، rate limiting پیشرفته، داشبورد تحلیلی سازمانی.

### ۱.۸ مشارکت‌ها

1. صورت‌بندی مسئلهٔ حکمرانی toolهای MCP در قالب یک محصول کوچک و قابل استفاده  
2. معماری Control Plane / Data Plane با دو نوع credential (session و platform token)  
3. فلو کاربرمحور: login → انتخاب از کاتالوگ → ساخت Gateway → اتصال کلاینت  
4. بستهٔ مستندات دفاع شامل مقاله، راهنما، API، ارزیابی و FAQ  

### ۱.۹ ساختار سند

بخش ۲ مبانی نظری را بیان می‌کند. بخش ۳ روش را شرح می‌دهد. بخش ۴ معماری، بخش ۵ پیاده‌سازی، بخش ۶ ارزیابی، بخش ۷ بحث و بخش ۸ نتیجه‌گیری است. در پایان، منابع و پیوست‌ها آمده‌اند.

## ۲. مبانی نظری و پیشینه

### ۲.۱ عامل ابزارمحور

عامل ابزارمحور سامانه‌ای است که برای رسیدن به هدف، علاوه بر استدلال زبانی، از ابزارهای خارجی استفاده می‌کند. کیفیت و ایمنی چنین عاملی فقط به مدل وابسته نیست؛ به این هم وابسته است که چه ابزارهایی در اختیارش قرار بگیرد.

### ۲.۲ پروتکل MCP در سطح لازم برای این کار

برای این پایان‌نامه، سه عملیات مهم‌اند:

| عملیات | نقش |
| --- | --- |
| `initialize` | آغاز ارتباط و اعلام قابلیت‌ها |
| `tools/list` | کشف ابزارهای قابل استفاده |
| `tools/call` | اجرای یک ابزار با آرگومان |

اگر access control فقط روی upstream پراکنده باشد، هر server باید جداگانه سیاست داشته باشد. یک لایهٔ واسط می‌تواند این سیاست را متمرکز کند.

### ۲.۳ مفهوم Gateway

Gateway نقطهٔ ورودی واحدی است که requestها را دریافت می‌کند، authentication انجام می‌دهد، و ترافیک را به سرویس‌های داخلی یا upstream هدایت می‌کند. در این کار، Gateway مخصوص ترافیک toolهای AI agent است؛ نه صرفاً یک reverse proxy عمومی.

### ۲.۴ Access control و principle of least privilege

طبق principle of least privilege، هر هویت فقط باید به حداقل resource لازم دسترسی داشته باشد. در MCP یعنی هر token فقط toolهای لازم را در `tools/list` ببیند و فقط همان‌ها را با `tools/call` اجرا کند. Allowlist روی tool پیاده‌سازی مستقیم همین اصل است.

### ۲.۵ پیشینهٔ مفهومی بدون اتکا به محصول خاص

در ادبیات سامانه‌های توزیع‌شده و امنیت API، ایده‌های زیر تکرار شده‌اند:

- نقطهٔ ورود واحد  
- جداسازی هویت مدیریتی و هویت اجرایی  
- ذخیرهٔ امن‌تر رازها  
- سیاست متمرکز به‌جای تکرار سیاست در هر سرویس  

این کار همان ایده‌ها را به حوزهٔ AI agent و MCP می‌آورد و در قالب یک سامانهٔ آموزشی کامل پیاده می‌کند. تمرکز متن بر مسئله و راه‌حل خود پروژه است، نه معرفی یا وابستگی به محصولات آماده.

### ۲.۶ شکاف مورد تمرکز

بین «اتصال خام به MCP» و «پلتفرم سازمانی بسیار پیچیده»، جای یک لایهٔ مینیمال و کامل خالی است؛ لایه‌ای که همزمان تجمیع، token، UI، دمو و ارزیابی داشته باشد. این پژوهش همین شکاف را هدف می‌گیرد.

## ۴. معماری و طراحی سامانه

### ۴.۱ نمای کلان

سه جزء اصلی:

1. Frontend مدیریتی  
2. Backend مربوط به Gateway  
3. Upstream نمونه (`demo-mcp`)  

جزئیات دیاگرام و جریان‌ها در سند [`architecture-fa.md`](architecture-fa.md) آمده است. خلاصه:

```text
کلاینت AI --Bearer--> /mcp --> سیاست grant --> پروکسی upstream
ادمین     --AdminKey--> /api --> SQLite
```

### ۴.۲ جداسازی Control Plane و Data Plane

- Control Plane: مدیریت موجودیت‌ها  
- Data Plane: اجرای پروتکل MCP  

این جداسازی هم امنیت نقش‌ها را بهتر می‌کند و هم دفاع را ساده‌تر توضیح می‌دهد.

### ۴.۳ مدل دادهٔ منطقی

موجودیت‌ها: User، Token، McpServer، Tool، TokenToolGrant.

نکتهٔ طراحی مهم: سیاست روی Token تعریف می‌شود؛ چون هر اتصال کلاینت عملاً با یک credential شناخته می‌شود.

### ۴.۴ الگوریتم اعمال سیاست

برای هر درخواست به `/mcp`:

1. خواندن Bearer Token  
2. محاسبهٔ hash و یافتن توکن فعال  
3. اگر نبود یا revoke شده بود → 401  
4. اگر method برابر `tools/list` بود → بازگرداندن toolهای grant شده و فعال  
5. اگر method برابر `tools/call` بود:  
   - اگر ابزار در grant نبود → خطا  
   - اگر بود → پروکسی به سرور مالک ابزار  
6. سایر methodهای پشتیبانی‌شده مانند `initialize` و `ping` پاسخ محلی می‌گیرند  

### ۴.۵ طراحی تجربهٔ کاربری برای دفاع

UI فارسی و RTL است و بدون login باز نمی‌شود:

1. Login  
2. نمای کلی  
3. Gateway من (ساخت token + ویرایش بعدی allowlist)  
4. کاربران (فقط ادمین)  
5. کاتالوگ MCP (افزودن چند سرور، Sync، حذف)  
6. اتصال  

لحظه‌های کلیدی محصول: ساخت Gateway توسط خود کاربر، نمایش یک‌بارهٔ platform token، و امکان کم/زیاد کردن toolها بدون تعویض token.

### ۴.۶ تصمیم‌های کلیدی طراحی

| تصمیم | توجیه |
| --- | --- |
| مینیمال بودن | تناسب با کارشناسی و دموی کوتاه |
| SQLite | حذف پیچیدگی عملیاتی |
| Hash توکن | کاهش ریسک افشای راز |
| Demo خیلی کوچک | تمرکز روی سیاست، نه دامنه |
| مستندات جدا از UI | UI اجرایی، docs دفاعی |

## ۵. پیاده‌سازی

### ۵.۱ پشتهٔ فناوری

| بخش | فناوری |
| --- | --- |
| Backend | FastAPI، SQLAlchemy، SQLite، httpx |
| Frontend | Next.js، React، Tailwind، الگوی کامپوننت‌های shadcn/ui |
| Demo | سرور MCP کاربردی با notes و tasks |
| اجرا | Docker Compose |

### ۵.۲ ساختار مخزن

```text
mcp-gateway/
  backend/     Gateway API و proxy
  frontend/    پنل مدیریت
  demo-mcp/    demo MCP
  docs/        مستندات کامل دفاع
  scripts/     ارزیابی خودکار
```

### ۵.۳ قابلیت‌های Backend

- مدیریت کاربر و توکن  
- ثبت چند سرور با نام یکتا، sync و حذف  
- تنظیم و به‌روزرسانی grant (`PUT .../grants`)  
- endpoint `/mcp` با فیلتر و پروکسی  
- endpoint کمکی ثبت demo  

### ۵.۴ قابلیت‌های Frontend

- Login با username/password  
- صفحهٔ Gateway من برای ساخت و ویرایش toolهای token  
- مدیریت کاربران توسط ادمین  
- کاتالوگ MCP با افزودن چند سرور، Sync و حذف  
- صفحهٔ Connect با snippet آماده  
- Proxy هم‌مبدأ `/gw` (شامل پاسخ‌های `204` برای حذف)  

### ۵.۵ Demo MCP

toolهای demo MCP:

- `notes_create` / `notes_list` / `notes_search` / `notes_get`  
- `tasks_add` / `tasks_list` / `tasks_complete`  

دامنه کاربردی است (یادداشت و کار)، اما هنوز کوچک می‌ماند تا داور روی سیاست دسترسی Gateway تمرکز کند.

### ۵.۶ نکات امنیتی پیاده‌سازی‌شده

- header جدا برای ادمین  
- Bearer برای کلاینت  
- hash مربوط به token  
- عدم ارسال token کلاینت به upstream  
- رد صریح `tools/call` غیرمجاز  

### ۵.۷ تکرارپذیری اجرا

با Docker Compose می‌توان کل پشته را بالا آورد. راهنمای گام‌به‌گام در [`user-guide-fa.md`](user-guide-fa.md) آمده است.

## ۶. ارزیابی

جزئیات اجرایی در [`evaluation-fa.md`](evaluation-fa.md) است. خلاصه:

### ۶.۱ سناریو A
فقط `notes_list` grant شده → `tools/list` فقط `notes_list` را برمی‌گرداند.

### ۶.۲ سناریو B
همان توکن → `tools/call` برای `tasks_add` رد می‌شود.

### ۶.۳ سناریو C
`tools/call` برای `notes_list` موفق است.

### ۶.۴ ابزار اجرا
اسکریپت `scripts/eval_scenarios.sh` مسیر آماده‌سازی و سه سناریو را خودکار می‌کند.

### ۶.۵ تفسیر علمی
Pass شدن A و B نشان می‌دهد فرضیه‌های کاری دربارهٔ فیلتر list و رد call برقرارند. این ارزیابی از نوع آزمون پذیرش رفتاری است و ادعای مقیاس‌پذیری ندارد.

- ارزیابی مشخص و تکرارپذیر  

### ۷.۳ محدودیت‌ها

- نبود OAuth سازمانی  
- نبود ممیزی پیشرفته  
- نبود سنجش بار بالا  
- تمرکز روی remote MCP  

این‌ها محدودیت اعلام‌شده‌اند، نه ضعف پنهان.

### ۷.۴ کاربردهای محتمل

- آزمایشگاه هوش مصنوعی دانشگاه  
- دموی تیمی کوچک  
- آموزش مفهوم Gateway و least privilege در ابزارهای عامل  

### ۷.۵ کارهای آینده

1. ارتقای client authentication به جریان استانداردتر سازمانی (مثل OAuth)  
2. audit log برای تمام `tools/call`ها  
3. quota و rate limiting  
4. اندازه‌گیری latency overhead مربوط به Gateway  
5. گروه‌بندی tool و templateهای آمادهٔ server  
6. در صورت نیاز واقعی: گسترش transportهای upstream/کلاینت فراتر از remote HTTP فعلی (بدون شلوغ کردن هستهٔ allowlist)

## ۸. نتیجه‌گیری

این پایان‌نامه نشان داد برای مسئلهٔ پراکندگی اتصال‌های MCP و ضعف access control در سطح tool، می‌توان یک MCP Gateway مینیمال طراحی و پیاده‌سازی کرد که واقعاً قابل استفاده باشد. سامانه با platform token، allowlist، رابط مدیریتی و ارزیابی رفتاری، پاسخ عملی به سؤال پژوهش می‌دهد. پیام نهایی کار این است:

**یک endpoint، یک platform token، فقط toolهای مجاز.**

## ۹. منابع

1. مستندات رسمی Model Context Protocol — مشخصات عملیات initialize، tools/list و tools/call.  
2. مستندات FastAPI — پیاده‌سازی خدمت وب و API.  
3. مستندات Next.js — پیاده‌سازی رابط کاربری.  
4. مستندات SQLAlchemy — ORM و مدل داده.  
5. مستندات Docker Compose — اجرای چندخدمتی تکرارپذیر.  
6. اصول امنیت API و مدیریت راز — مباحث ذخیرهٔ hash به‌جای راز خام و جداسازی نقش‌ها.  
7. principle of least privilege در کنترل دسترسی سامانه‌ها — مبنای نظری allowlist ابزار.  

> در نسخهٔ تحویلی دانشگاه، قالب ارجاع گروه (APA/IEEE/…) و تاریخ بازیابی منابع وب را دقیق کنید. نام دانشجو، استاد راهنما و دانشگاه را در صفحهٔ عنوان درج کنید.
